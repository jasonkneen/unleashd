## 08:23Z — Root cause of Wave Sim return-thread discontinuity: startup rekey migration orphans every coordination thread
_owner_thread 406b7b7a-6587-43dc-abe2-929eb6a28741_

2026-09-23. Successor evidence to the 2026-09-22 notes (final proposal 2026-09-22T12:02:02.780Z:545471d6…, same-thread note after it), which left the discontinuity's mechanism "unproven". Reviewer: Buddies Development Lead (Opus 5.5 session). Evidence only; no fix applied or approved.

Mechanism: server/src/lifecycle/session-loader.ts:190-196 hydrate() rekeys any active config record whose conversationId is not a UUID to a random UUID (store.rekeyConversation, config-store.ts:395). The rekey was meant for legacy records that used a provider session id as their app id. But coordination threads use deterministic non-UUID ids by design: return threads `buddy-return-<hash>` (dispatch-service.ts:493) and worker threads `buddy-run-<id>` (run-executor.ts:329). After any server restart, the first hydrate of their provider session moves the record to a UUID. Then the next return run: getConversationRecord('buddy-return-…') returns null, so branch/handoff/launches are undefined (run-executor.ts:438). getConversation also misses, so it takes the createConversation path (run-executor.ts:505-529). That creates a fresh record under the same commandId with no branch, no knowledgeScope, and the Buddy profile default config instead of the launch config. The pre-launch snapshot prompt is skipped silently.

Disk proof (~/.agent-viewer/conversation-config/v1, read 2026-09-23): four records carry commandId coordination-return-buddy-return-6adf4d232bf6f1948f60b60469457337 (5f55da25 05:56Z, 434db97c 07:51Z, 9f26aad4 10:04Z no-branch effort=high, c4450879 11:51Z). They are successive incarnations of one deterministic id. The 10:04Z record matches the executor path exactly (created 10ms after run start, allowedBuddyOperations present, no knowledgeScope). Systemic: of 524 coordination records, all 496 with a provider session are UUID-keyed and all 28 still under a native id have no session. 47 return commands map to 64 records; 10 have more than one incarnation. Worker until_done continuations after a restart likewise start blank.

Implications for the 2026-09-22 proposal: (1) the continuity item is a small, well-defined bug fix: rekey only when the record id equals one of its own provider session ids, not when the id is not a UUID. The executor should never fresh-create a return thread whose record is missing. (2) The "parent-outcome briefing" would have been empty in this case: the CEO return context had buddyProjectId=null; the CEO's outcome lived only in owner chat. (3) The owner "run to completion" path already exists: POST /api/buddies/projects/:id/run (routes.ts:453), which runs until_done with maxRuns/maxDurationSeconds. Self-send of bounded work is also allowed (coordination.js:230-240). The wave_sim CEO never used managed mode. (4) The proposal to wake the human chat conflicts with the invariant at run-executor.ts:661-677; once the rekey is fixed, the return thread already is the continuous lead thread.

Also: the three 2026-09-22 proposal docs were swept into unrelated commit ad1aab5 (channel-browser null checks) by a concurrent session.
